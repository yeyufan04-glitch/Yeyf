# 系统结构与判定逻辑

## 一条主线

```text
客户贸易材料
  -> Document AI：识别、抽取、确定性核验
  -> 结构化交易事实
  -> TEG：组织来源、支持和冲突关系
  -> ESE：输出 COMPLETE / PARTIAL / CONFLICT / MISSING
  -> AI 业务分析：形成可验证 Claim
  -> CAV：Calibration -> Audit -> Verify
  -> AI Assurance Certificate
  -> 标准事项流转 / 例外事项人工处置
```

## TEG 与 ESE

TEG 的核心对象不是“文件”，而是 `Trade Case -> Fact -> Evidence Source`。同一事实可以由客户材料、外部独立证据、银行内部证据共同支持，也可以产生冲突。

ESE 状态：

- `COMPLETE`：满足证据模板且不存在关键冲突。
- `PARTIAL`：已有支持，但独立来源数量、范围或必要说明不足。
- `CONFLICT`：重要来源之间出现尚未解决的矛盾。
- `MISSING`：必要证据不存在。

状态描述证据充分性，不等于交易真实性结论。

## CAV

- Calibration：按具体任务维护样本量、观察准确率与保守下界，不使用笼统“模型准确率”。
- Audit：把模型输出拆成事实型和解释型 Claim，分别验证证据。
- Verify：在动作执行前读取银行策略门禁；关键冲突、低可靠度或无支持 Claim 触发禁止动作。

## Demo 合成冲突

- 合同：总量 1,000 件，允许分批装运。
- 发票与装箱单：数量 1,000 件，金额 USD 800,000。
- 提单、原产地证与报关回执：本批数量 800 件。
- 付款指令：USD 800,000，付款用途写明 800 件。

系统可以证实“数量不一致”和“合同允许分批”；只能支持“可能为分批履约”；不能把“发票笔误”当作事实。因此禁止自动汇款，并要求更正材料与补充分批履约说明。

## 生产落地边界

本包没有连接单一窗口、海关、承运人或工商银行核心系统，没有生产级 WORM、电子签名或真实模型 Benchmark。生产阶段需在银行内网完成授权、接口治理、规则审批、Shadow Mode 验证和审计存储接入。
